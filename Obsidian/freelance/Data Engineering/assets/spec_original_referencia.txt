# 4. BLOQUE I — SQL Y OPTIMIZACIÓN

---

## 4.1 Optimización de búsquedas en SQL

### Temas a estudiar

- SARGability
- uso de índices
- funciones en `WHERE`
- conversiones de tipos
- operadores negativos
- filtros selectivos
- scans vs seeks

### Aprender

Explicar por qué una condición como:

```sql
WHERE YEAR(fecha) = 2026
```

puede impedir un uso eficiente de un índice.

Compararla con:

```sql
WHERE fecha >= '2026-01-01'
  AND fecha < '2027-01-01'
```

Explicar también el problema de:

```sql
WHERE CAST(cliente_id AS VARCHAR) = '123'
```

frente a una comparación usando el mismo tipo de dato.

### Concepto clave

Una consulta es más eficiente cuando el motor puede utilizar directamente un índice para localizar las filas necesarias.

### Incluir

- Index Seek
- Index Scan
- Table Scan
- predicates
- selectividad
- estadísticas

---

## 4.2 Operadores negativos

Estudiar:

```sql
<>
NOT
NOT IN
NOT EXISTS
```

Explicar por qué los predicados negativos pueden ser menos amigables para índices.

Aclarar que no significa que estén "prohibidos".

Lo importante es entender:

- selectividad
- índices disponibles
- cardinalidad
- estadísticas
- plan de ejecución

---

## 4.3 Funciones analíticas de ranking

Estudiar:

```sql
ROW_NUMBER()
RANK()
DENSE_RANK()
PERCENT_RANK()
```

### Comparación obligatoria

Usar un ejemplo como:

| Empleado | Salario |
|---|---:|
| Ana | 1000 |
| Luis | 1000 |
| Pedro | 900 |
| Carla | 800 |

Explicar el resultado de:

```sql
ROW_NUMBER() OVER (ORDER BY salario DESC)
```

```sql
RANK() OVER (ORDER BY salario DESC)
```

```sql
DENSE_RANK() OVER (ORDER BY salario DESC)
```

### Regla rápida

- `ROW_NUMBER`: siempre asigna un número distinto.
- `RANK`: empates reciben el mismo rango y deja saltos.
- `DENSE_RANK`: empates reciben el mismo rango sin dejar saltos.
- `PERCENT_RANK`: expresa la posición relativa entre 0 y 1.

---

## 4.4 Índices clustered y nonclustered

Estudiar:

- clustered index
- nonclustered index
- primary key
- key lookup
- covering index
- heap

### Explicar

Un índice clustered determina cómo se organizan las filas en la estructura de almacenamiento del índice.

Un índice nonclustered mantiene una estructura separada con:

- clave indexada
- referencia/localizador hacia la fila

### Comparar

| Característica | Clustered | Nonclustered |
|---|---|---|
| Cantidad típica por tabla | 1 | varios |
| Organización principal de filas | Sí | No |
| Estructura separada | No de la misma forma | Sí |
| Bueno para rangos | Muy bueno | También puede serlo |
| Puede incluir columnas | depende del motor | Sí, normalmente |

### Aclaración

No afirmar que un índice siempre mejora una consulta.

Los índices tienen costo en:

- `INSERT`
- `UPDATE`
- `DELETE`
- almacenamiento
- mantenimiento

---

## 4.5 UNION vs UNION ALL

Estudiar:

```sql
UNION
UNION ALL
```

### Explicar

`UNION` elimina duplicados.

Conceptualmente equivale a:

```text
combinar resultados
+
eliminar duplicados
```

Esto suele exigir trabajo adicional como:

- sort
- hash
- distinct

`UNION ALL` simplemente concatena los resultados.

### Regla rápida

Si sabes que los datos ya son únicos y **no necesitas eliminar duplicados**, normalmente:

```sql
UNION ALL
```

es más eficiente.

---

## 4.6 EXCEPT e INTERSECT

Estudiar:

```sql
EXCEPT
INTERSECT
```

### Aprender

- `EXCEPT`: filas del primer conjunto que no aparecen en el segundo.
- `INTERSECT`: filas presentes en ambos conjuntos.

Compararlos con:

- `NOT EXISTS`
- `INNER JOIN`

---

## 4.7 Particionamiento de tablas

Estudiar:

- table partitioning
- partition key
- partition pruning / elimination
- particiones por fecha
- mantenimiento de particiones

### Explicar

El particionamiento **no mejora automáticamente todas las consultas**.

Es útil cuando los filtros coinciden con la estrategia de partición.

Ejemplo:

Tabla de ventas de miles de millones de registros particionada por año.

```sql
WHERE fecha >= '2026-01-01'
  AND fecha < '2027-01-01'
```

El motor podría leer solo la partición relevante.

### Analizar cuándo puede NO ayudar

- tablas pequeñas
- queries que leen todas las particiones
- mala elección de partition key
- exceso de particiones
- filtros que no usan la columna de partición

---

## 4.8 Encontrar registros sin correspondencia

Problema:

> encontrar clientes que no tienen transacciones.

Estudiar:

```sql
NOT EXISTS
NOT IN
LEFT JOIN ... IS NULL
```

### Ejemplo

```sql
SELECT c.*
FROM clientes c
WHERE NOT EXISTS (
    SELECT 1
    FROM movimientos m
    WHERE m.cliente_id = c.cliente_id
);
```

### Explicar especialmente

El problema de `NOT IN` cuando la subconsulta puede contener `NULL`.

Ejemplo:

```sql
WHERE cliente_id NOT IN (
    SELECT cliente_id
    FROM movimientos
)
```

Si existen `NULL`, la semántica SQL de tres valores puede producir resultados inesperados.

### Regla rápida

Para anti-joins, `NOT EXISTS` suele ser una opción muy robusta y expresiva.

## 4.9 Planes de ejecución

Estudiar:

- execution plan
- estimated execution plan
- actual execution plan
- optimizer
- cost estimation
- cardinality estimation
- statistics

### Explicar

El optimizador utiliza estadísticas para estimar:

- número de filas
- selectividad
- costo de operadores
- estrategia de joins
- uso de índices

### Concepto crítico

Las estadísticas desactualizadas pueden provocar malas estimaciones de cardinalidad y planes subóptimos.

### Comparar

| Plan | Ejecuta query | Datos reales de ejecución |
|---|---|---|
| Estimado | No | No |
| Actual | Sí | Sí |

---

## 4.10 Estadísticas de tablas

Estudiar:

- histograms
- cardinality
- selectivity
- auto statistics
- update statistics

Explicar por qué mantener estadísticas actualizadas ayuda al optimizador.

## 4.11 DDL, DML y DCL

Crear tabla:

| Tipo | Propósito | Comandos |
|---|---|---|
| DDL | estructura | `CREATE`, `ALTER`, `DROP`, `TRUNCATE` |
| DML | manipulación de datos | `INSERT`, `UPDATE`, `DELETE`, `MERGE` |
| DQL | consulta | `SELECT` |
| DCL | permisos | `GRANT`, `REVOKE` |

Aclarar que la clasificación exacta puede variar ligeramente según literatura o motor.

## 4.12 CTE

Estudiar:

```sql
WITH nombre_cte AS (...)
SELECT ...
FROM nombre_cte;
```

### Ejemplo

```sql
WITH ventas_cliente AS (
    SELECT
        cliente_id,
        SUM(total) AS total_compras
    FROM ventas
    GROUP BY cliente_id
)
SELECT *
FROM ventas_cliente
WHERE total_compras > 1000;
```

### Aprender

Los CTE permiten:

- hacer queries más legibles
- separar pasos lógicos
- reutilizar una expresión dentro de una sentencia
- construir CTE recursivos

### Importante

Un CTE no implica necesariamente que se materialice físicamente como una tabla temporal.

El optimizador puede integrarlo en el plan.

# 6. BLOQUE III — TESTING Y CALIDAD

---

## 6.1 Pruebas de regresión

Estudiar diferencia entre:

### Confirmation / Retesting

Comprueba que un defecto específico fue corregido.

### Regression Testing

Comprueba que un cambio no rompió funcionalidades que antes funcionaban.

### Ejemplo

Se corrige el módulo de login.

- Retesting: comprobar específicamente el bug corregido.
- Regresión: probar además registro, recuperación de contraseña, sesiones, permisos, etc.

---

## 6.2 Pruebas unitarias

Características:

- prueban unidades pequeñas
- son rápidas
- deben ser aisladas
- no deberían depender de servicios externos
- facilitan detectar errores temprano

### Ejemplo

```python
def sumar(a, b):
    return a + b

def test_sumar():
    assert sumar(2, 3) == 5
```

---

## 6.3 Functional vs Non-functional Testing

### Funcional

Pregunta:

> ¿Hace el sistema lo que debe hacer?

Ejemplos:

- login
- generar factura
- registrar usuario
- comprar producto

### No funcional

Pregunta:

> ¿Qué tan bien funciona?

Ejemplos:

- rendimiento
- seguridad
- escalabilidad
- disponibilidad
- usabilidad

### Regla rápida

```text
Functional = qué hace
Non-functional = qué tan bien lo hace
```

---

## 6.4 Pirámide de pruebas

Estudiar la pirámide de Cohn:

```text
        UI / End-to-End
       ---------------
        Integration
       ---------------
          Unit
```

Más pruebas abajo, menos arriba.

### Razón

Las pruebas unitarias suelen ser:

- rápidas
- baratas
- estables

Las pruebas E2E suelen ser:

- lentas
- costosas
- más frágiles

## 6.5 Niveles de pruebas

### Acceptance Testing

# 8. BLOQUE IV — APACHE SPARK

---

## 8.1 Arquitectura de un clúster Spark

Estudiar:

### Driver

Proceso principal de la aplicación.

Responsabilidades:

- construir el DAG
- planificar stages
- solicitar recursos
- distribuir tareas
- recopilar resultados/metadatos

### Executors

Procesos ejecutados en worker nodes.

Responsabilidades:

- ejecutar tasks
- almacenar datos en cache
- devolver resultados al Driver

### Cluster Manager

Ejemplos:

- Standalone
- YARN
- Kubernetes

Se encarga de gestionar recursos del clúster.

### Importante

HDFS puede usarse como sistema de almacenamiento, pero **no es un componente obligatorio de la arquitectura de Spark**.

---

## 8.2 Procesamiento distribuido

Ventajas:

### Escalabilidad

Añadir nodos para aumentar capacidad.

### Paralelismo

Dividir un problema en múltiples tareas.

### Rendimiento

Procesar varios fragmentos simultáneamente.

### Tolerancia a fallos

Spark puede reconstruir particiones utilizando lineage cuando determinadas tareas fallan.

---

## 8.3 Transformations y Actions

### Transformations

Ejemplos:

```python
df.filter(...)
df.select(...)
df.withColumn(...)
df.groupBy(...)
```

Normalmente son lazy.

Spark construye un plan antes de ejecutar.

### Actions

Ejemplos:

```python
df.count()
df.collect()
df.show()
```

Las acciones disparan la ejecución del plan.

### Regla rápida

```text
Transformation = describe trabajo
Action = dispara trabajo
```

---

## 8.4 Lazy Evaluation

Explicar por qué Spark espera antes de ejecutar:

Permite al optimizador analizar varias operaciones juntas y mejorar el plan.

Ejemplo:

```python
df2 = df.filter(...)
df3 = df2.select(...)
df4 = df3.groupBy(...)

df4.show()
```

La ejecución real ocurre cuando se llama una acción como `show()`.

---

## 8.5 Narrow vs Wide Transformations

### Narrow

Una partición de salida depende de pocas particiones de entrada.

Ejemplos:

```text
map
filter
select
```

Normalmente no requieren shuffle.

### Wide

Una partición de salida depende de varias particiones de entrada.

Ejemplos:

```text
groupBy
reduceByKey
join
distinct
repartition
```

Normalmente requieren shuffle.

---

## 8.6 Shuffle

Definir shuffle como redistribución de datos entre particiones o executors.

Es costoso porque puede implicar:

- red
- serialización
- memoria
- disco
- sorting
- transferencia entre nodos

### Ejemplo

```python
df.groupBy("country").count()
```

Para agrupar todos los registros de un mismo país, Spark puede tener que mover datos entre particiones.

---

## 8.7 DAG

DAG significa:

```text
Directed Acyclic Graph
```

Representa dependencias entre operaciones.

Estudiar:

- jobs
- stages
- tasks
- dependencies

### Jerarquía

```text
Application
   ↓
Job
   ↓
Stage
   ↓
Task
```

---

## 8.8 Stage boundaries

Un nuevo stage suele aparecer alrededor de una dependencia que requiere shuffle.

Ejemplo:

```python
df.filter(...)
  .groupBy(...)
  .count()
```

El `groupBy` puede generar un shuffle y separar stages.

### Precisión importante

Las acciones disparan un **job**.

Los shuffles son los que típicamente marcan límites entre **stages** dentro del job.

---

## 8.9 Spark vs MapReduce/Hadoop

Explicar que una de las razones principales de Spark para workloads iterativos es su capacidad para mantener datos intermedios en memoria.

No simplificar diciendo que "Spark nunca usa disco".

Spark puede usar:

- RAM
- disco
- almacenamiento distribuido

dependiendo de la operación y configuración.

### Ventaja típica

Reducir escrituras repetidas a disco puede acelerar algoritmos iterativos y pipelines analíticos.

---

## 8.10 Persistencia y caching

Estudiar:

```python
df.cache()
df.persist()
```

### `cache()`

Usa un nivel de almacenamiento por defecto.

### `persist()`

Permite especificar una estrategia de almacenamiento.

Puede utilizar:

- memoria
- disco
- memoria + disco

### Cuándo usar

Cuando el mismo DataFrame será reutilizado varias veces.

### Cuándo evitar

Si se usa una sola vez.

---

## 8.11 Spark SQL functions vs UDF

Comparar:

```python
from pyspark.sql import functions as F
```

Funciones nativas:

```python
df.withColumn("name_upper", F.upper("name"))
```

UDF:

```python
@udf(...)
def custom_function(...):
    ...
```

### Explicar

Las funciones nativas permiten a Spark entender y optimizar la expresión.

Pueden beneficiarse de:

- Catalyst Optimizer
- code generation
- predicate pushdown
- optimización del plan

Las UDFs pueden introducir una "caja negra" para el optimizador.

### Regla rápida

Si Spark ya tiene una función nativa que resuelve el problema, preferirla antes de crear una UDF.

---

## 8.12 Cross Join

Estudiar:

```sql
SELECT *
FROM Tabla1
CROSS JOIN Tabla2;
```

Si:

```text
Tabla1 = N filas
Tabla2 = M filas
```

resultado:

```text
N × M filas
```

### Ejemplo

1 millón de filas × 1 millón de filas:

```text
1,000,000,000,000
```

combinaciones potenciales.

### Conclusión

Un cross join accidental puede ser extremadamente costoso.

---

## 8.13 Buenas prácticas Spark SQL

Estudiar:

- filtrar temprano
- seleccionar solo columnas necesarias
- evitar `SELECT *`
- evitar cross joins innecesarios
- utilizar funciones nativas
- reutilizar DataFrames mediante cache cuando tenga sentido
- revisar particionamiento
- reducir shuffles
- broadcast joins para tablas pequeñas cuando sea apropiado
- revisar planes con `explain()`

Ejemplo:

```python
df.explain("formatted")
```

# 9. ARQUITECTURA LAMBDA

---

## 9.1 Concepto

Lambda Architecture combina normalmente:

### Batch Layer / Cold Path

Procesamiento histórico de grandes volúmenes.

### Speed Layer / Hot Path

Procesamiento de eventos recientes o streaming.

### Serving Layer

Expone los resultados para consultas o aplicaciones.

Representación:

```text
                 ┌──────────────┐
                 │ Data Source  │
                 └──────┬───────┘
                        │
             ┌──────────┴──────────┐
             │                     │
        Cold / Batch           Hot / Stream
             │                     │
             └──────────┬──────────┘
                        │
                  Serving Layer
                        │
                      Views
```

## 23.16 Agrupación y centroides

### Concepto matemático

Para un grupo de puntos:

## 23.18 Distancia euclidiana

La función de la prueba calcula:

```text
d = sqrt((x - prom_x)^2 + (y - prom_y)^2)
```

### Implementación del notebook

```python
def distancia_euclideana(x, y, prom_x, prom_y):
    return sqrt(
        (x - prom_x) * (x - prom_x)
        +
        (y - prom_y) * (y - prom_y)
    )
```

### Estudiar

- distancia euclidiana
- coordenadas
- métricas espaciales
- nearest point

### Interpretación

El centro con menor distancia al promedio de su grupo se considera el más céntrico según la regla de la prueba.

|---|---|---|---|

- evita parte del costo de parsing de JSON

Después de estudiar el spec completo y el notebook, debes poder recibir un dataset desconocido y seguir este proceso mental:

```text
1. Inspeccionar schema y calidad
        ↓
2. Limpiar y tipar
        ↓
3. Definir granularidad
        ↓
4. Transformar
        ↓
5. Aplicar reglas de negocio
        ↓
6. Agregar / rankear
        ↓
7. Enriquecer mediante joins
        ↓
8. Validar resultados
        ↓
9. Revisar escalabilidad
        ↓
10. Elegir formato de salida
```

Ese flujo resume gran parte de lo que realmente está evaluando la prueba técnica de Data Engineering.
